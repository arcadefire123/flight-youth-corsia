### 1.1 6단계 ⑤ 「페르소나·유저 시나리오」

현재 가이드북에는 후보 3명이 표로만 있다. 아래로 교체한다. **확정: P1 주 페르소나 / P2 보조 / P3 언급만.**

> **인물 이름과 부서명은 설명을 위해 지어낸 가상의 예시다.** 실존 인물·조직과 무관하며, 소속 기관의 업무 범위만 실제 제도를 따랐다. 검토 대상 「한빛항공」도 3단계에서 만든 가상 항공사다.

| 구분 | 페르소나 | 제일 먼저 보고 싶은 것 |
|---|---|---|
| **주** | **공단 검토 담당자 「정유진 과장」** (한국교통안전공단 항공환경처) | 이 보고서를 그대로 받아도 되는가(판정) → 무엇이, 어느 조항 위반인가 |
| 보조 | 항공사 탄소 담당자 「박성호 대리」 (중형 항공사 안전환경실) | 최종 상쇄의무량(예산) → 지금 내면 걸릴 곳 |
| 언급 | 검증기관 심사원 | 재계산값과 보고값의 차이가 중요성 임계 안인가 |

**P1 정유진 과장** — 국토부 위탁을 받아 이행의무자가 낸 배출량보고서를 검토하고 상쇄의무량을 산정·통보한다. 4월 30일 제출 직후 한두 달에 업무가 몰리고, 한 사람이 여러 항공사를 맡는다. 엑셀·PDF를 오가며 합계를 수기로 대조하는 데 시간이 가장 많이 들고, 보완을 요청하려면 근거 조항을 매번 다시 찾아야 한다.

> 시나리오 — 한빛항공의 2024년 보고서와 비행 기록을 올린다. **몇 초 만에** 「불만족 · 종합점수 25.8 · 위반 41건(치명 22)」이 맨 위에 뜬다. 치명 위반부터 훑으며 각 줄의 근거 조항을 확인하고, X-12를 펼쳐 보고값 2,051,986 t과 재계산값 1,807,081 t의 차이 244,905 t이 중요성 임계 36,142 t을 넘었음을 본다. 결과를 내려받아 보완 요청 공문에 붙인다.

**P2 박성호 대리** — 연료 데이터로 보고서를 만들어 제출하고 상쇄의무량만큼 배출권을 사서 말소한다. 전담이 한두 명이고 CORSIA만 보지도 않는다. 제출 후 보완 요청을 받는 것과 배출권 예산을 잘못 잡는 것이 가장 부담이다.

> 시나리오 — 사내 데이터를 올려 「265,773 t」을 확인해 배출권 구매 품의를 올린다. 위반 목록에서 EMP 방법 불일치를 발견해 제출 전에 고치고 다시 돌려 「만족」을 확인한 뒤 제출한다.

**P3 검증기관 심사원** — 시행령 제8조에 따라 보고값을 직접 재계산해 비교해야 하고, 그 차이가 중요성 기준 안인지로 검증의견이 갈린다. 실사 전 데스크 리뷰에서 집중할 곳을 추리는 용도로 쓴다. **별도 화면을 만들지 않는다** — 필요한 「재계산값 ↔ 보고값 ↔ 중요성 임계」는 위반 목록 X-12 상세에 이미 다 들어간다.

**설계에 준 결론** — 세 사람 모두 "맨 위에 결론"을 원하지만 그 결론이 서로 다르다(판정 / 상쇄의무량 / 재계산 차이). 셋을 한 상자에 나란히 두면 하나의 화면으로 덮을 수 있어, 역할별 화면 분리를 하지 않기로 했다.

### 1.2 9단계 「무엇을 하나 ① 종합점수 설계」

"후보는 다음과 같고, 9단계에서 정합니다"를 확정 내용으로 교체한다.

- **확정 방식**: 심각도 가중 감점 + 판정별 상한. 치명 5 / 중요 2 / 경미 1 / 정보 0의 배점을 주고 잃은 배점 비율로 환산.
- SKIPPED는 분모에서 제외, 위반 건수는 점수에 미반영(목록에만 표시), 상한은 전체 점수에만 적용.
- 판정별 상한 100 / 89 / 59 — **ICAO 기준이 아니라 팀 자체 보조 기준**임을 반드시 함께 적는다.
- 실측: 정상본 100.0점(만족), 오류주입본 25.8점(불만족). 계층별은 형식 17.8 · 임계값 76.2 · 일관성 12.5 · 정성 75.0.

### 1.3 9단계 「② 화면 설계」

현재 표(맨 위·가운데·아래)를 확정 레이아웃으로 교체한다.

| 위치 | 영역 |
|---|---|
| 1 | **결과 요약 상자** — 최종 판정 · 종합점수 · 최종 상쇄의무량 + (불만족이면) 경고 줄 + 계층별 점수 4개 |
| 2 | 위반 목록 — 심각도 순, **근거 조항은 펼치지 않아도 각 줄에 표시**, 줄 클릭 시 수치·예시·감점 산식 펼침 |
| 3 | 정성 검증 — 「AI 참고용 · 최종 판정 아님」 배지 |
| 4·5 | 계산 상세 / 원본 데이터 — 기본 접힘 |

- "요약 고정"은 스크롤을 따라다니는 고정이 아니라 **맨 위에 한 상자로 묶는다**는 뜻이다(전체 캡처 용이, Streamlit에서 안정적).
- 불만족일 때 최종 상쇄의무량 옆 경고 문안: *"검증을 통과하지 못한 데이터로 계산한 값입니다. 보완 후 다시 계산해야 합니다."* 숫자를 숨기지는 않는다.
- 종합점수는 소수점 1자리로 표기.

## 5. 해소된 발견 사항 — X-22 규칙 제목

`consistency.py` 254행의 제목이 "동일 노선 **평균** 대비"로 남아 있어 위반 목록에 틀린 설명이 뜨는 문제였다. **"동일 노선 중앙값 대비"로 정정했다.** 판정 로직은 원래 중앙값이었으므로 결과 수치는 변하지 않는다. 같은 일이 다시 생기지 않도록 `tests/test_verify.py`에 "X-22 제목에 중앙값이 들어 있어야 한다"는 테스트를 넣었다.

이 패턴(로직은 고쳤는데 표시 문자열이 옛 설명으로 남음)은 현황 인덱스 §3의 "데이터를 다시 의심하는 습관" 사례로 쓸 만하다.

### 함께 고친 것 — 규칙 제목이 위반 목록에서 거꾸로 읽히는 문제

규칙 제목은 "미해결 데이터 공백 **없음**", "배출량 재계산 **일치**"처럼 **요건을 서술한 문장**이다. 규칙 목록 문서에서는 맞지만, 위반 목록에 그대로 나오면 문제가 없다는 뜻으로 읽힌다.

규칙 제목(`title`)은 규칙 문서와 일치해야 하므로 그대로 두고, **화면 표시용 위반 문구를 따로 뒀다**(`corsia/verify/violation_text.py`, 규칙 63개 전부 등록). 펼친 상세에는 규칙 제목도 함께 보여 어느 규칙인지 확인할 수 있게 했다.

| 규칙 | 제목 (문서·규칙 정의) | 위반 문구 (화면) |
|---|---|---|
| X-19 | 미해결 데이터 공백 없음 | 미해결 데이터 공백 **있음** |
| X-12 | 배출량 = 연료질량 × 연료전환계수 재계산 일치 | 배출량 재계산 **불일치** |
| F-04 | 배출량보고서 필수 15개 항목 전부 포함 | 배출량보고서 필수 15개 항목 중 **누락 있음** |

빠진 규칙이 생기면 `check_all.py`가 「위반 문구」 항목에서 잡는다.

## 5-1. 브라우저 확인 후 고친 것 (2026-10-24)

가이드북 10단계 「팀원 필수 — 각자 PC에서 실제로 돌려보기」에서 예고한 종류의 문제가 실제로 나왔다. 가이드북이나 발표 이야기 거리에 넣을 만하다.

| 문제 | 원인 | 조치 |
|---|---|---|
| 한국어 윈도우에서 `pip install -r requirements.txt`가 `UnicodeDecodeError`로 실패 | 파일은 UTF-8인데 pip이 cp949로 읽음. 한글 주석이 원인 | `streamlit>=1.30` 한 줄만 남김. **외부 도구가 직접 읽는 파일엔 한글 금지** 규칙 신설, `check_all.py`가 점검 |
| 1100px에서 45곳, 800px에서 78곳 한글이 단어 중간에 끊김 | 브라우저 기본 줄바꿈이 한글을 글자 단위로 끊음 | 화면 전체 `word-break: keep-all; overflow-wrap: anywhere;` (팀장 실측 1곳·5곳으로 감소) + 좁은 목록에서 근거 칸 유연화 |
| 사용자 PC 설정에 따라 어두운 화면으로 열림 | Streamlit 기본값이 시스템 테마를 따름 | `.streamlit/config.toml`로 밝은 모드 고정. engine 폴더에서 실행해야 적용됨 |

가이드북 10단계 「팀원 PC 실행」 설명에 **"반드시 engine 폴더에서 `streamlit run app.py`"**, **"다른 브라우저로 열려면 `--server.headless true` 후 localhost:8501 직접 열기"** 두 줄을 넣으면 좋다.

## 5-2. 팀장 직접 시험 후 고친 것 (2026-10-25)

| 문제 | 원인 | 조치 |
|---|---|---|
| 800px(사이드바 열림)에서 위반 목록 감점 41줄이 안 보임 | 최소 폭 620px + 가로 스크롤 | 목록 폭 620px 이하에서 세 줄 쌓기 |
| 계산 상세 표 「상쇄 대상 배│출량」 끊김 | 표 첫 칸 87px | 첫 칸 줄바꿈 금지 + 가로 스크롤, 표 칸 `overflow-wrap: normal` |
| 한국어 엑셀 CSV 올리면 UnicodeDecodeError | 엑셀 기본 저장이 cp949 | UTF-8 실패 시 cp949 재시도 + 테스트 |
| `KeyError: 'fuel_type'` 같은 오류 | 입력 점검 없음 | 엔진에 넣기 전 점검, 사람이 읽는 문구 + 접힌 기술 원인 |
| 비행 기록만 올려도 「만족 / 100.0」만 크게 나옴 | 판정 보류 35건 안내 없음 | 판정 아래 안내 (판정은 그대로) |
| 결과 JSON에 PC 사용자 이름이 든 전체 경로 | 경로를 그대로 저장 | 폴더 이름만 |
| 펼친 줄에 `reported_t 2051985.9600000002` | 영어 이름·긴 소수 | 대응표로 한글 이름·천 단위 쉼표 |
| 정성 검증을 확인하지 못했는데 「모두 작성됨」 | 판정 보류를 통과처럼 표시 | 「확인하지 못했습니다」, 일부면 나눠 표시 |
| 오류주입본을 보는데 정상본 명령 안내 | 고정 문구 | 샘플에 맞게, 파일 올리기면 숨김 |
| 판정 보류 사유에 `documents` 등 코드 이름 | 대응표 없음 | 한글 이름 + 누락 테스트 |
| (추가 발견) 올린 적격연료 파일을 계산엔진이 안 읽음 | 파일 이름 고정 | 올린 파일을 같은 이름으로 저장, 안 올리면 감축량 0 |
| (추가 발견) 문단만 단어 중간에서 끊김 (1280px 「들어갑│니다」 등) | Streamlit 문단 규칙이 keep-all을 덮어씀 | `word-break: keep-all !important` |

실측 방법: 작업 환경에 conda-forge의 Firefox(헤드리스)와 Selenium을 설치해, 오류주입본 41줄을 띄우고 줄 3개와 계산 상세를 펼친 채 7개 폭에서 ① 감점 숫자가 목록 상자 안에 있는지 ② 규칙 번호가 한 줄인지 ③ 한글-한글 사이에서 줄이 바뀐 곳이 있는지 ④ keep-all이 아닌 한글 요소가 있는지를 쟀다. 결과는 7개 폭 모두 0. 이 과정을 발표의 「직접 재 보지 않으면 모른다」 사례로 쓸 수 있다 — 넓은 창 두 곳에서 맞았던 것이 운이었음을 다른 폭에서 드러냈다.
